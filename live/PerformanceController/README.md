# Audio performance adapter

This adapter is the fixed-source Audio recovery block. It is deliberately separate from the installed prototype. Device contacts, gestures, screens and optimistic presentation are outside Live. `surface.py` accepts complete semantic commands, sends immediate bounded ACKs and publishes coalesced actual facts.

Set `configuration.TARGET_SET` to the exact trial Set path before a coordinated installation. An optional nonempty `TARGET_SETS` tuple instead allows only its explicitly named paths, for example a cheap fixture and the heavy Set. There are no wildcard matches; Untitled always fails closed. Switching allowed paths detaches the old retained backend before rebinding and rejects commands and modal permission until the current path is bound. The Set needs unique `[R1]` through `[R8]` groups for tiles in use. Each usable recording group needs an existing rightmost direct subgroup named `[Remote]`. No migration, instrument/FX cloning or heavy-Set changes happen automatically.

`PARAMETER_BINDINGS` maps zero-based group indices to four target dictionaries. Absent groups use the first four sends. A target is `{'kind':'send','index':0}` or `{'kind':'device','device_path':[0],'parameter_index':3}`; nested paths alternate device/chain/device indices. A device target can instead name its unique parameter, for example `{'kind':'device','device_path':[0],'expected_device_name':'Random Rev + Delay V2','parameter_name':'Reverb'}`. Optional `expected_device_name` and `expected_parameter_name` guards reject an unrelated rack or indexed parameter before reading its value. A missing or ambiguous named parameter never falls back to `parameter_index`, even if both keys are present.

Bindings retain Native identities and their original indices. A moved/replaced target, changed guard name or newly ambiguous macro disables its own white control instead of resolving onto a different parameter; restoring the old structure does not silently rebind it. Resolution and guard/uniqueness checks run during discovery and background observation. Parameter writes use the retained object without traversing the rack or parameter list. Volume and pan remain independent. Every group seed publishes all six parameter facts before availability; value128 explicitly disables an unavailable control rather than inventing a starting value.

For the existing Temple racks, use `device_path:[0]`, rack guard `Random Rev + Delay V2` and `parameter_name:'Reverb'`/`'Delay'` for the first two white controls. The third uses `device_path:[1]`, rack guard `Stereo Random Filter` and `parameter_name:'FX Vol'`. Keep the fourth `{'kind':'send','index':3}`. These named targets preserve the existing private configuration without guessing Native macro indices.

The semantic MIDI contract is [performance_protocol.md](../../bridge/native/performance_protocol.md). Explicit Native CC forwarding is part of the adapter, including the separate generation handshake and modal-permission query. Channel16 CC78 explicitly starts a fresh transport session, clearing only wire parsing/deduplication/observation revisions and reseeding current Native facts, even when its generation repeats after a helper restart. Active recording/prepared state remains intact. CC79 remains an idempotent keepalive. Matching complete command replay ACKs the last result without repeating a mutation. Partial, conflicting or wrong-generation frames do not execute.

## Performance and preparation

Mute and parameter commands use retained Native targets. Recording allocation consumes a prepared destination only; it cannot create tracks/scenes or configure routing in MIDI dispatch. Once a destination is ready, Begin, Accept and Accept+Next may enqueue their already planned Native launch directly from the semantic command callback. `enqueue_ready()` uses retained identities and the existing admission guards; it performs no discovery, allocation, routing or full backend tick. Later-window admission, actual observation and preparation remain in display callbacks. Short Native setters and structural calls have separate diagnostic timing events. Parameter normalization reserves zero for the exact minimum, and pan64 maps to center.

`backend.py` separates active-clip observation from background maintenance. Active observation reads only currently playing slots, not tracks multiplied by scenes. Occupancy inventory progresses at no more than64 slot reads per background callback. Own recording/deletion transitions update only the affected row. Known own track creation updates retained topology rather than forcing whole-Set rediscovery. Manual structural/name changes invalidate retained discovery; this slower work is outside the touch command handler.

Preparation reuses a quiet compatible Audio track with an empty current phrase slot, otherwise creates one directly before `[Remote]`. This is the interior insertion point verified in the Native placement experiment; there is no read-only `group_track` write. A bounded selection repair restores the previous track/scene/slot after Live's automatic selection effect. Only one repair lifecycle is active at once. New tracks retain their factory devices and configure only the fixed external mono input1, Monitor Off and implicit actual group output. The output path is observed rather than selected by an ambiguous display label. Every ready target is checked again before allocation, including manually changed routing.

New recording tracks and reused default-named trial tracks inherit `INPUT_NAME` and `INPUT_COLOR_INDEX` during background preparation. The current fixed-source profile is T-Bone, palette index64 from the prepared input track. Custom track names and existing clips are preserved. Appearance is cosmetic and cannot block a valid recording destination; no source catalog scan or metadata writes occur in command dispatch.

Known take transitions and global bar-clock facts are published before synchronous preparation work. A pre-maintenance flush and final flush share one six-fact budget per display callback, including during an initial seed backlog. This exposes actual recording promptly without inventing a start or claiming that Native track creation became asynchronous.

The active group's next reserve has priority while recording. Maintenance performs at most one structural/routing mutation per step and defers near a pending launch boundary. One Native call remains synchronous within Live; this adapter does not claim an independent Native execution thread. A missing reserve admits a bounded preparing state, then starts at the next safe captured boundary once ready. Preparation failure produces a terminal take fact and allows another user intent; an uncertain created object is retained and never blindly duplicated. If explicit Set setup supplies a previously missing rightmost `[Remote]` subgroup, actual structural discovery clears only that missing-anchor failure and resumes preparation without requiring Begin. Uncertain creation and routing failures remain latched.

## Prepared capacity and overflow

The chosen starting setup has at least four compatible Audio lanes in each loop group, with `ALLOW_AUDIO_TRACK_CREATION=True`. Four is a prepared starting capacity, not a limit. Change that capacity directly in the Set by adding configured Audio lanes before `[Remote]`; the adapter does not enforce or recreate a particular count on startup. Existing extra tracks and historical clips remain in place. There is no shared reserve or automatic track movement.

Existing compatible lanes are reused first. When the fourth lane is recording, background maintenance may already create and configure a fifth as the next destination. This preserves the prepared same-bar Accept+Next path. Audio insertion can produce an audible artifact in the heavy Set even when performed manually; the user explicitly accepts that cost for automatic overflow. New phrases reuse empty slots in existing lanes without changing previous clips.

For an explicitly prepared-only setup, set `ALLOW_AUDIO_TRACK_CREATION=False` before the adapter starts. That mode never creates Audio tracks/scenes or resumes routing configuration. Known unavailable capacity rejects Begin promptly through the existing brief error feedback. Accept+Next without a spare leaves the current recording running. Clear and confirmed own cleanup invalidate cached capacity, allowing existing lanes to be reused on a fresh phrase row. A stopped transport alone is not an off-air setup gate because monitored inputs may remain audible.

The four-to-five regression test covers no creation through the first three recordings, background overflow before `[Remote]`, selection restoration, a same-bar handoff, Cancel and historical clip preservation after Clear. Fixed-mode tests separately assert zero structural/routing writes and full-pool behavior. The actual eight-lane R3 trial over Bluetooth at256samples had clean audio and direct interaction, supporting preallocation for the ordinary recording path. These tests do not promise inaudible overflow insertion or source-routing changes.

## Audio input patches

`AUDIO_SOURCES=()` preserves the fixed-source baseline. To enable the two-input Audio block, configure two dictionaries, for example `({'name':'T-Bone','helper_name':'[Input 1]'}, {'name':'SM-58','helper_name':'[Input 2]'})`. Source Audio tracks must be unique by name inside the unique `[Inputs]` hierarchy. Their physical inputs and devices are prepared in Live, never cloned. They require Monitor In, Sends Only output and all source sends at their minimum. This lets processing run without a second audible output.

Finish explicit stopped-Set preparation before activating the Audio-input Control Surface: helper names, source/Post FX routes, implicit helper outputs and source processing must all be final. After preparing an already active Set, choose None and then the same Control Surface again. This creates a fresh adapter/backend that discovers the completed setup without restarting Live or reloading Python modules. The current discovery cache does not automatically adopt newly renamed input helpers, source-catalog renames or newly configured canonical helper routes while active. Do not use private reload hooks or silent migration. Ordinary managed recording-lane creation continues through its existing retained-topology path.

When reopening a prepared Set, Live may expose the saved tracks before their routing properties are ready. Missing source profiles are completed from the two retained source/helper candidates during background observation. This retries no graph discovery or routing writes and adds no helper routing reads once both profiles are ready. A retained source must still have its configured name. This startup recovery requires no manual Control Surface reselection.

Every rightmost `[Remote]` subgroup needs two explicitly prepared Audio helpers named `[Input 1]` and `[Input 2]`. Each helper taps the corresponding source Post FX and uses its implicit parent output. Muted means unassigned; unmuted means assigned. Only the sole monitor owner's assigned helpers use Monitor In; all others stay Monitor Off. Helpers remain inside the technical subgroup and never consume recording lanes. The adapter creates no helpers on touch or during performance. Missing infrastructure fails locally.

Canonical preconfigured helper route values identify sources. Display names alone are insufficient because recorded tracks may also be named T-Bone. The adapter matches offered routing values by Native equality, with an exposed identifier used only when present. Portable equality across receivers is a Native installation gate; simulator equality is not a substitute. Ordinary track identities and actual helper configuration remain authoritative. Slow helper observation adopts manual Live changes when no own helper plan is outstanding. Configured sources remain retained while unavailable; restoring source readiness clears only known readiness failures, never uncertain Native mutation failures.

Semantic keys48–55 admit absolute source masks, and57 selects the monitor owner. These paths perform no graph scans or source routing. Retained helper mute/monitor updates are coalesced and bounded to six short setters per callback, disabling old monitoring paths before enabling new ones. Source routing and lane creation remain background maintenance. Repeated taps replace the desired state; releasing fingers does not cancel admitted work. Preparation failure rolls back only the still-current intent to the confirmed patch and restores a known ready destination where possible. An older failure cannot undo a newer patch or monitor-owner choice. The input tile's pending state distinguishes admitted selection from a fully prepared recording bundle. An unavailable source already selected may be removed; adding a new unavailable source is rejected. A selected bundle with any missing source cannot record.

Each take captures one or both source profiles. A prepared bundle reserves a distinct quiet musical lane per selected source in the same phrase row. Start and Accept+Next preflight all destinations, then enqueue consecutive Native requests on the same planned boundary. Live does not offer an atomic multi-track transaction. Member ownership, actual anchors, source clip labels/colors and cleanup are tracked individually under one logical token. Retry/Cancel handle the whole owned bundle; old-token cancellation retains the existing scoped replacement semantics. A partial or uncertain enqueue is never replayed. Failure containment preserves the old accepted handoff clips and cleans only the new owned material. Missing start or finish confirmation terminates rather than leaving the controller in an indefinite countdown. A manually stopped member ends the remaining owned capture while preserving all clips. A failed promised handoff reports the replacement token, matching the device's optimistic context.

Both sources consume two Audio lanes per take. Background lookahead prepares another whole bundle, preserving the existing immediate Accept+Next flow. Only quiet lanes with an empty target slot can be reconfigured; earlier phrase clips retain their own metadata. Changing patch selection cannot retarget the current take's captured members. Four initial lanes remain a Set-level inventory rather than a fixed maximum.

## Recording

`recording_core.py` retains the previously tested Native scheduling, actual start/finish observation and sample-coverage normalization. Its allocator is abstract; the prepared adapter supplies all destinations. It uses current actual leftmost playing loop timing for each take, with the Native `clip.start_time + loop_start` anchor. Variable take lengths, next-safe-bar Accept, immediate Cancel/Retry cleanup and base-loop-wrap Begin remain unchanged. Accept+Next reserves its replacement before finishing and schedules both the old finish and new start for the same next safe bar. A late pre-enqueue admission moves both targets together to a later bar; it never waits for the base-loop wrap. The two Native fire calls are consecutive but are not an atomic Live transaction. Transition events retain planned targets and actual anchors, and an observed following-anchor mismatch is logged instead of replaying a launch. The user accepted this handoff in the USB cheap-Set trial; Native timing and arming behavior under Bluetooth and heavy-Set load remain separate gates. Completion/admission facts may coalesce directly to the latest context; no intermediate display phase is required. Cancel during a promised handoff cancels only the following take and retains the old Accept. A bounded old-token alias is scoped to that exact following transaction, or to Retry's logical pending replacement and then its admitted Native Take, until a new-token command is observed or the take completes/replaces; it has no arbitrary time cutoff. An unavailable prepared destination rejects Next while the old take keeps recording, without creating a track or silently stopping into a wait.

Manual deletion of completed clips is observed through current slots. Completed transaction bookkeeping does not dereference its old Native clip wrappers, which Live may invalidate after deletion. Deleting earlier accepted clips also leaves an independently active take running.

Recording tokens reject late controls for a replacement take. A Native launch is marked issued before calling Live; an ambiguous exception cannot cause automatic replay. Confirmed current unaccepted recordings alone may be deleted by Cancel/Retry. Existing accepted clips and manual content are preserved. Clear stops only its group immediately and plans a fresh unused phrase row; it deletes no clips. Native start/finish facts, rather than countdown expiry, decide whether recording happened.

Global meter/click/tempo controls share this semantic path. Tap Tempo computes denominator-aware quarter-note BPM without invoking Native `tap_tempo`, which could start transport under a user preference. The prior helper health heartbeat and modal permission protocol remain available independently of graphics output.

## Verification and limits

Run `python3 -m unittest discover -s live/PerformanceController -p 'test_*.py' -v` from the repository root. Focused checks cover the actual command callback, Native CC registration, duplicate/partial frames, path gates, direct-command graph-read budgets,2000-scene active-take read bounds, prepared reserve/reuse and overflow, variable transaction tokens, failed/ambiguous launch, safe-boundary Accept, guarded named/indexed binding identity, missing-anchor recovery, Clear and modal controls. `fake_native.py` is an explicit queued Native simulator, not Live or hardware timing evidence.

The matched helper, device programs and adapter passed the user's complete USB and Bluetooth cheap-Set trials, including mute chords, mixer, recording/layers, Retry, Cancel, same-bar Accept+Next and metronome switching. Source naming/color was also checked in Live and the saved Set. This is the accepted Audio baseline, not a production rollout. The chosen all-group setup combines prepared capacity with the explicitly accepted insertion cost above. A46.9ms track-creation result in a cheap Set does not establish heavy-Set behavior.

`STATUS_PATH` optionally writes private JSON readiness at most twice per second. The snapshot uses retained Python bookkeeping only: known groups, prepared group/row pairs, maintenance stages, failures and the current take transaction. It performs no extra Native reads or MIDI output. Serialization/filesystem errors are contained and add at most one diagnostic event; they never stop musical commands or publish a global controller failure. Unexpected display failures also reach the existing throttled private trace/status paths. Identical repeated failures are deduplicated, `display_error` records the current error, and successful recovery clears it.
