# Audio performance adapter

This is the current Audio controller, installed as `LightpadAudioInputs` through the [matched installer](../../bridge/README.md#audio-performance-installation). The Lightpad owns contacts, gestures, screens and optimistic feedback. `surface.py` accepts semantic commands, sends bounded immediate ACKs and publishes changed Live facts. The [wire contract](../../bridge/native/performance_protocol.md) describes the matched device and bridge protocols.

## Set and source setup

The private configuration requires `AUDIO_SOURCES = 'catalog'` and explicit absolute `TARGET_SETS` paths, or one `TARGET_SET`. Untitled and unlisted Sets are unavailable. Switching allowed paths detaches the old backend before binding the new Set; commands cannot act on the previous Set. After Save As or moving a Set, update the path configuration through a staged installation.

Mark usable loop groups uniquely with `[R1]` through `[R8]`. Each needs a rightmost direct subgroup named `[Remote]`, used as the insertion boundary for prepared music lanes. Four direct Audio lanes per group are the starting inventory. All subgroup descendants are excluded from recording allocation.

Put Audio source tracks under the unique `[Inputs]` group. Organizational subgroups are flattened in Live track order. Up to seven Audio sources are exposed by the current patch program; MIDI instruments are outside this implementation. Source names and colors appear on the pad, with names cached locally for scrolling while held. Source tracks require Monitor In, Sends Only output and all sends at minimum. Their hardware inputs and effects stay on the original tracks. Recording lanes tap their Post FX signal, bypassing effects on organizational parent groups.

Source routing uses Native `RoutingType.attached_object` to identify the original Track. A recording lane with the same name cannot substitute for the source. Discovery retains actual Native objects and completes unavailable startup routing profiles in background callbacks. Duplicate source UUIDs, missing sources and unsupported routing remain unavailable rather than resolving by an ambiguous label. Restoring a known source's readiness clears only readiness failures, never an uncertain Native mutation.

## Patch state and monitoring

`audio_patch_state.py` stores source UUIDs on original source tracks, selected UUIDs on R-groups, and one monitoring-owner index on `[Inputs]`, using namespaced, versioned `Track.get_data/set_data` values. Selection survives catalog reordering by identity. Missing selected UUIDs remain unresolved; another source is never silently substituted. New groups start without a selected source.

Keys48–55 admit absolute seven-bit source masks;57 selects the monitoring group without changing its source selection. These commands update cached intent only. They perform no graph scan, routing or metadata writes. Retaps replace the desired state, and releasing contacts does not cancel admitted preparation. Changed metadata is coalesced and flushed during maintenance. A preparation failure rolls back only its still-current intent. An older failure cannot overwrite a newer patch or monitoring choice.

Native user data is included in an actual Live Set save. Metadata-only changes neither mark a clean Set modified nor add an Undo step, and Cmd+S on that otherwise clean Set does not write them. Actual routing and monitoring changes are normal Live edits and have been checked to trigger saving in the small Native trials. The adapter performs no automatic save or artificial parameter toggle. Save the Set after changing its working setup.

`direct_monitoring.py` uses the actual prepared recording lanes with Monitor Auto and controller-owned arms. One group owns live monitoring. Completed clips keep playing; the next idle bundle carries live input. Accept and Accept+Next prepare the handoff so the next recording can start at the same boundary. Brief double monitoring around that transition is accepted. There is no source-by-group monitoring helper matrix.

Prepared lanes receive a namespaced ownership marker containing their group and source UUID. Reopening recovers an armed lane only when that marker, its actual direct group parent, source identity, Post FX routing and monitoring state agree. Arm state alone is insufficient. Unmarked manual arms and active manual recordings are not adopted. Stale or invalid saved ownership never permits touching a different track.

Manually deleted tracks invalidate Native handles, including their listener and monitoring references. Discovery retires these handles and affected prepared reservations, then rebuilds from surviving direct Audio lanes. Boost.Python `ArgumentError` is handled at these Native boundaries; ordinary Python type errors still surface. A removed lane is never a reason to replay an earlier recording command.

## Performance and preparation

Mute, volume, pan and mapped FX use retained Native targets. Begin, Accept and Accept+Next enqueue already prepared launches directly when their timing window is ready. Recording admission performs no allocation, routing, structural work or full backend tick. The bridge dispatches commands before device feedback, and the device draws gestures and optimistic values locally.

Background preparation reuses the first eligible direct Audio lane in Live track order. Names, existing effects, mixer settings and an already matching source route do not affect priority. The lane must be quiet, unfrozen and empty in the current phrase row; external arms, active/triggered destinations and current/following take members are excluded. Preparation updates source routing, monitoring, source name/color and ownership metadata while preserving devices, output routing, volume, pan, sends, mute and earlier clips. An earlier lane becoming free replaces a later reserve during maintenance.

After a Native start or finish has been issued, structural and routing preparation waits until the actual transition is observed. Live's synchronous allocator can take longer than a bar, so a short proximity margin cannot protect the transition. Long count-ins whose Native launch is not yet issued still permit lookahead. Clear invalidates preparation for the old phrase row while retaining any already created track for reuse.

A take reserves one destination per selected source. All members share a phrase row, transaction token and timing boundary, while retaining independent Audio clips. Its captured source list cannot be retargeted by a later patch choice. Background lookahead prepares another complete bundle during recording. Accept, Retry, Cancel and Accept+Next operate on the bundle. Native member calls are sequential rather than an atomic Live transaction.

With `ALLOW_AUDIO_TRACK_CREATION=True`, missing lanes are inserted after the music tracks and before `[Remote]`. Native creation is synchronous: it can audibly disturb a heavy Set at small buffers and block Live steering while the call runs. When preparation first needs an additional track, maintenance publishes a Busy ticket (fact6/3) and yields. The device waits for contacts to finish, paints Busy and confirms on a later repaint; the bridge drains admitted commands and returns semantic key58. A matching ticket permits the complete missing bundle to be prepared in later callbacks, including any additional insertions, routing and final reserve validation. The whole device stays locked until that bundle is ready or preparation fails or is cancelled. Existing-stock preparation does not enter Busy. Callback heartbeats retain the same ticket every half-second while work continues. An unstarted request expires after ten seconds without performing Native work; changed group/row/source context and protocol reseeding also invalidate permission. After protocol reseeding, an unfinished overflow job must reacquire Busy before continuing its retained routing work. Uncertain Native failures clear Busy and are never replayed. This handshake makes the accepted preparation pause visible; it does not make Native creation asynchronous. Keep creation disabled to use only the manually prepared inventory. Selection restoration returns Live to the previous track/scene/slot after Live's automatic selection change. With creation disabled, existing lanes can still be routed and reused, but no new Audio tracks or scenes are created. Missing capacity is temporary readiness, not a latched Native failure. It gives the established brief failure feedback; an unavailable next bundle leaves the current recording running. Adding direct Audio lanes manually or freeing earlier slots lets maintenance prepare another bundle automatically. Retry the gesture once capacity is ready; rejected commands never replay.

Active observation reads current playing slots. Occupancy inventory progresses at no more than64 slots per maintenance callback. Known take/global clock facts flush before synchronous preparation, sharing a six-fact display budget with the final flush. Structural/name edits invalidate discovery outside command dispatch. Cooperative callbacks do not make Native calls asynchronous.

## Mixer bindings

`PARAMETER_BINDINGS` maps zero-based groups to four white controls. Unconfigured groups use their first four sends. A target is `{'kind':'send','index':0}` or `{'kind':'device','device_path':[0],'parameter_index':3}`; nested paths alternate device/chain/device indices. A device target may name its unique parameter and guard the device, for example `{'kind':'device','device_path':[0],'expected_device_name':'Random Rev + Delay V2','parameter_name':'Reverb'}`.

The Temple racks bind white controls1/2 to `Reverb` and `Delay` in `Random Rev + Delay V2` at device path `[0]`; control3 to `FX Vol` in `Stereo Random Filter` at `[1]`; control4 remains send index3. A missing or ambiguous named parameter never falls back to an indexed parameter. Moved or replaced targets disable only their control instead of writing somewhere else. Volume and pan remain independent; zero maps to the exact parameter minimum, pan64 to center, and value128 disables unavailable device controls. Every group seed publishes all six controls before enabling its tile.

## Recording and recovery

Each take uses the current leftmost eligible playing loop as its timing reference, retaining that reference for this recording only. Begin/Retry align to its wrap when possible. Accept ends at the next safe bar; an unissued press too close to the boundary moves to the following bar. Accept+Next ends the old take and starts the prepared replacement at the same safe boundary, without another base-loop countdown.

Native clip flags and anchors confirm actual start/finish. Countdown expiry is not confirmation. Issued but uncertain actions are observed and never blindly replayed. Retry/Cancel remove only owned unaccepted material; accepted handoff clips survive cancellation of the following take. A bounded old-token alias applies only to its exact replacement transaction. Missing confirmation terminates instead of leaving an endless countdown. Manual deletion of completed clips uses current slots without dereferencing invalid historical clip wrappers.

Clear stops only its group and advances to a free phrase row, deleting no clips. Global meter/click/tempo share the semantic path. Tap computes denominator-aware quarter-note BPM without Native `tap_tempo`, which could start transport under a user preference.

## Diagnostics and verification

`STATUS_PATH` writes private readiness JSON at most twice per second from cached Python bookkeeping, including source availability, desired/prepared selections, maintenance jobs and storage pending/errors. It performs no extra Native reads or MIDI writes. Filesystem/serialization failures are contained and produce at most one diagnostic event. Unexpected display failures reach the throttled trace/status paths; repeated identical failures are deduplicated and successful recovery clears `display_error`.

Run `python3 -m unittest discover -s live/PerformanceController -p 'test_*.py' -v`. Fake Native tests cover the command fast path, routing/ownership guards, saved-state recovery, bundle scheduling, bounded preparation and failure containment. Joined compiled-device/C++/Python tests are documented in the [bridge guide](../../bridge/README.md#matched-audio-input-mode). Offline checks do not establish audible timing or Bluetooth responsiveness. [Validation](../../VALIDATION.md) records the physical gates separately.
